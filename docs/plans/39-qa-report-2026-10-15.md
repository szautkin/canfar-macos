### Step 1 — `show_compute_run` names the image

- `ComputeRunDetail` gains `image: String?`, absent for runs from before it was kept, the same as
  `list_compute_runs`.
- Test: a selected run's detail carries its image (`RemoteComputeScreenTests`).

### Step 2 — A failed auto-apply names its proposal

- The answer becomes "auto-apply failed, and nothing waits in Pending (proposal `<id>`): `<why>`".
  `withdraw_proposal` on that id answers `withdrew: false, state: withdrawn` while the outcome is kept.
- Test (VerbinalKit): a failing apply's answer carries the id, and the withdraw answers as above.

### Step 3 — The ADQL check finds a bare column no table has

- `bareAmbiguities` becomes one walk over bare column names, with the same conditions as today:
  - one SELECT only (a subquery is left alone);
  - none of these: a table, an alias, a name given with AS, a function, a USING column, a keyword.
- It adds one more condition: a word right after an expression in the select list is an alias written
  without AS (`SELECT ra r`).
- For each name it finds:
  - **Several tables have it:** ambiguous, as today.
  - **No table has it:** unknown, but only when every FROM table's columns are known. A table with no
    columns listed means "cannot tell".
    - With one table, the message is the existing one, "caom2.Plane has no column "x"", with the
      nearest name as the fix.
    - With several, it is a new message, "No table here has a column "x"", in English and French.
- The ADQL editor runs the same check as the person types, so a false mark would be worse than none.
- Tests, in `ADQLValidatorTests`:
  - **Stays clean:**
    - `*` and `COUNT(*)`;
    - `TOP n` and `DISTINCT`;
    - `CAST(x AS DOUBLE)`;
    - an ORDER BY alias, and an implicit alias;
    - `CONTAINS(POINT('ICRS', ra, dec), CIRCLE('ICRS', 10, 20, 1)) = 1`;
    - `IS NOT NULL`, `BETWEEN … AND`, `IN (…)`;
    - `CASE WHEN … THEN … ELSE … END`, `GROUP BY … HAVING`;
    - a subquery, and `JOIN … USING (obsID)`;
    - keywords in any case;
    - words in literals and in comments.
  - **Caught:**
    - a misspelled column in the select list;
    - one in WHERE;
    - one in a two-table join.
- On screen: the ADQL editor marks the misspelled column, seen with `capture_view` or a real-window
  test.

### Step 4 — The texts say what waits, and when a session continues

**What waits.** What applies at once is the person's choice, kind by kind
(`get_current_view.permissions`). Only "What every assistant is told" always waits, and removing what
an assistant made is a kind of its own. Change:

- `AGENTS.md`, "The person reviews your changes";
- `withdraw_proposal`'s description: "every destructive one" becomes "any whose kind the person asks to
  approve";
- the Pending button's help, "…destructive changes always wait here" (English and French), and the
  comments beside it (`ContentView.swift:285`, `ContentViewToolbars.swift:203`);
- the verb-class sentences in `AutoApplyPolicy` ("Destructive: it always waits…", "a delete always
  waits…"). The app always passes a kind instead, so these are reached only by a tool without one.
  Confirm no proposing tool lacks a kind, then reword them so they promise nothing the app does not do.

**When a session continues.** Only as long as the assistant's client keeps the same `Verbinal mcp`
process; a client that starts a new one starts a new session, which the person allows again. The
manual already says this (chapter 12, English and French). Bring these into line with it:

- `AGENTS.md`, "Call it once…";
- `AgentSession.instructions`;
- `start_session`'s description and its `alreadyStarted` note.

The guardrails that hold descriptions (`ToolShapesTests` and others) are updated with them.
