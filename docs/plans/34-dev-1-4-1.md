## S — One session per assistant

### What happens today

- Every socket connection to the app gets a new session: `MCPBridgeService.session = UUID()`, "a relay
  reconnecting after Verbinal restarts is a new one".
- The relay (`Verbinal mcp`, `ResilientBridge`) reconnects by itself after Verbinal restarts and replays the
  client's `initialize`. The assistant believes it still has its session; every tool then answers
  `sessionRequired`, it calls `start_session` again, and the person sees the approval window again for an
  assistant they already allowed.
- Within one connection, `start_session` is already idempotent: `SessionApprovals.ask` answers an allowed
  session at once. The answer does not say it was already allowed, so an assistant cannot tell a first
  start from a repeated one.
- Approvals live in memory only: an app restart forgets them.

### What we want

1. An assistant calls `start_session` once. While its relay lives, a reconnection after Verbinal restarts
   keeps the same session: the same id, the same instructions, the same log. No new window.
2. A second `start_session` from an allowed session answers at once that it was already allowed: when, the
   instructions, and "do not call it again".
3. A session that was declined, or whose request was cancelled (the window closed, the assistant stopped
   waiting), is not allowed; the next `start_session` asks the person again, as now.
4. An allowed session ends after an hour without a call, connected or not; the person sets how long in
   **Settings ▸ AI Agent**. The next call answers `sessionRequired` with the reason (`idle`), and
   `start_session` asks the person again.

### Design

| Part | Job |
|---|---|
| **Relay identity** (`MCPCore`) | `ResilientBridge` makes one session id when the relay starts, and sends it with every connection to the app, in the replayed `initialize`'s `_meta` under `AgentSession.metaKey`. |
| **Bridge** (`MCPBridgeService`) | Takes the relay's id when it is a valid UUID; otherwise, as for direct connections and tests, a new one. One rule, in `AgentSession`. |
| **Approvals** (`SessionApprovals`) | Remembers the allowed sessions on disk (`Application Support/Verbinal/AgentSessions/approvals.json`), with the time of each one's last call. It reloads them at launch, and forgets one idle longer than the setting, one the person ends, and all when **Allow external AI agents** is turned off. Declined and cancelled requests are never remembered. One rule decides "still allowed": the gate and `start_session` both ask it. |
| **The setting** | **Settings ▸ AI Agent ▸ End an idle session after**: 15 minutes, 1 hour (the default), 4 hours, 12 hours, 1 day. The person's: an assistant reads it in `describe_app`, and cannot change it. |
| **Tool** (`StartSessionTool`) | Answers `alreadyStarted: true` with `allowedAt`, the instructions and a one-line note when the session was allowed before; `false` on a first start. |
| **Session log** | The same session's log continues; a reconnection writes one line, "reconnected after Verbinal restarted". |
| **The person's control** | **Settings ▸ AI Agent ▸ Session Logs** gains **End Session** on an open session: it forgets the approval, so the next call asks again. |

The words that tell assistants how to start (`AgentSession.instructions`, `describe_app`, AGENTS.md, the
tool's description) say once: call it once; a reconnection keeps your session.

### Tests first

- The relay sends the same id on two connections; the bridge takes it, and makes a new one without it.
- An approval survives a reload of `SessionApprovals`; one idle past the setting (15 minutes and 1 hour,
  with a test clock), an ended one, and one after agents were turned off do not.
- An idle session's next call answers `sessionRequired` with `idle`; a call within the time keeps it
  alive.
- A second `start_session` answers `alreadyStarted: true` with no window; after a decline or a cancel, it
  shows the window again.
- `SessionGateTests` and `MCPEraTests` still pass.

## A — A 401 that recovers

### What happens today

On a 401, `NetworkClient` asks `AuthLifecycleController.handleNetworkUnauthorized` whether to retry once:

| The stored token, checked with `/whoami` | What happens now |
|---|---|
| Still valid | The request is retried once, with the token stamped again. If the service says 401 again, the request fails; nothing else happens. |
| Expired | `handleTokenExpired` starts a silent sign-in in the background, and the handler answers "do not retry", so **the request that hit the 401 fails**, even when the silent sign-in succeeds a moment later. |
| CADC unreachable | The request fails; the connectivity path tries again later. |

The silent sign-in (`silentReauth`) is right: the stored token first, then, when **Remember me** was on, a
new sign-in with the password kept in the Keychain (this Mac only). It shows the sign-in sheet only when
that cannot work: no password is stored, or CADC refuses it (it is then cleared). After the sheet, the
person returns to where they were.

### What we want

1. A 401 never loses the request that met it when Verbinal can sign in again by itself: the request waits
   for the renewal, then is retried once with the new token.
2. One renewal at a time: many 401s at once share it; none starts its own sign-in.
3. A token CADC still accepts but a service refuses (401 again after the retry) gets one fresh sign-in
   with the stored password, then one more try.
4. The sign-in sheet appears only when no renewal can work (no password stored, or CADC refuses it), and
   says why: "Your CADC session ended. Sign in to continue."
5. An assistant's tool answers what it does now: `signInNeeded` with `retry: afterSignIn`; the person
   signs in, never the assistant.

### Design

| Part | Job |
|---|---|
| **`AuthLifecycleController.renew()`** | The one renewal: single-flight (one `Task` shared by every caller), the stored token, then the stored password; answers renewed, offline, or ended. The 401 handler, the launch check and the connectivity retry all call it (today the launch and connectivity paths call `silentReauth` themselves). |
| **The 401 handler** | Every 401 goes through `renew()`, so many at once check the token and sign in once (a check resets the client's shared token: done one at a time). A first 401: a token CADC accepts is retried; an expired one waits for the sign-in, then is retried. A second 401 on a token CADC accepts: one fresh sign-in when a password is stored, one more try; without one, the request fails and the session stays. Ended: the existing `onSessionExpired` (leave Portal and Storage, show the sheet), and the request fails as `unauthorized`. A sign-in in the last 30 s counts for the 401s after it. The renewal's own requests are never held for it. |
| **The sign-in sheet** | Takes a reason, shown above the fields when the session ended rather than at a first sign-in. |
| **Decision log** | One line per renewal: renewed, kept (offline), or ended, with the rule (as today's `signedInAgain` / `signInLost`). |

### Tests first

- An expired token with a stored password: the request that met the 401 is retried once and succeeds;
  CADC sees one sign-in for five concurrent 401s.
- No stored password, or a refused one: no retry, the sheet with its reason, the password cleared when
  refused.
- A second 401 on a token CADC accepts: one fresh sign-in, one more try, then the request fails and the
  session stays; without a stored password, no sign-in, and the session stays.
- Offline: no sign-in attempt, the stored credentials kept, the request fails as offline.

## F — Files of an observation, in Research

### What happens today

- The observation detail's **Files** tab lists every file of every plane. Its download button opens the
  file's address in the browser (`openURL`): nothing is downloaded by Verbinal, and Research does not know.
- A Research record holds one file (`localPath`). An assistant's `download_observation` with `file` fetches
  a chosen file (`DownloadService.downloadToTemp(publisherID:file:)`), and its record then points at that
  file instead of the one before.
- The person's **Download** asks where to save (`ResearchModel.download` → save panel); an assistant's goes
  straight to Downloads (`placeInDownloads`). Two paths for one job.
- Everything else Verbinal saves without asking (cutouts, figures, result exports, session logs) goes to
  `~/Downloads` (`DownloadsFolder.url`), a folder the person cannot change.

### What we want

1. The download button of a file in **Files** downloads that file with Verbinal, into the download
   folder: no browser, no question.
2. The person sees where files go, where they download them ("Saving to ~/Downloads", **Change…**), and
   in **Settings ▸ General ▸ Downloads**. It is `~/Downloads` until they choose another folder.
3. Research records it: the observation, kept or created, now has that file, among its others, with
   where it is.
4. The file's button becomes a trash button: **Remove File…** deletes the file from this Mac (after asking)
   and removes it from the record. The button is a download button again.
5. Research's observation detail lists the observation's files, each with where it is, open, show in
   Finder and the trash button.
6. The main **Download** of an observation goes the same way: the download folder, no save panel.

### Design

| Part | Job |
|---|---|
| **The download folder** (`DownloadFolder`) | The one owner of where Verbinal saves what nobody chose a place for; it replaces `DownloadsFolder.url` everywhere (observation files, the main **Download**, cutouts, figures, result exports, session logs). `~/Downloads` by default; another folder is chosen with an open panel and kept with an app-scope bookmark, as `LocalFolderAccessStore` keeps granted folders. When the chosen folder is gone (a drive not mounted, a stale bookmark), a download goes to `~/Downloads` and says so. |
| **Where the person sees it** | A line under the **Files** tab and in Research's detail: "Saving to <folder>", **Change…**. **Settings ▸ General ▸ Downloads**: the folder, **Change…**, **Show in Finder**, **Use Downloads**. An assistant's answers say where each file went; the folder is the person's to change. |
| **Data** | `files` on the record (`KeptFile`: the file's name, its archive URI, where it is, its bookmark, size, when, who). Research's records are a JSON file, not the database (`ObservationStore`), so no migration: a record kept before reads with no files. A file's name is unique within its record. |
| **Model** | `KeptFile`, `DownloadedObservation.files`, and `LocalFile`: the one way a record's main file and its other files are reached (path, bookmark, exists, problem), pulled out of the record (DRY). Today's `localPath` stays the observation's main file for 1.4.1 (decision 2); the main file answers to its name too. |
| **One download path** | `ResearchFiles.download(file:of:)`: fetch (`DownloadService`), place in the download folder (`DownloadFolder.move`, never over a file), and record the path and, outside `~/Downloads`, a bookmark. The **Files** tab, Research's detail, the main **Download** and the assistant's `download_observation` all call it. Records made with the save panel before keep their bookmarks and open as before. |
| **One removal path** | `ResearchFiles.remove(file:of:)`: delete the file, then its row; the kind "Remove files on this Mac" for an assistant (it waits by default). |
| **View** | The **Files** tab asks Research for each file's state: not kept (download), downloading (progress), kept (open, trash). The detail stays a view of the observation; it does not own downloads. |
| **Tools** | `download_observation` `file` records the file; `remove_downloaded_file` takes `file`; `get_downloaded_observation` lists the files. |

### Tests first

- Downloading a file creates the record when there is none, adds the file when there is, and never
  replaces another file of the record or a file in Downloads.
- Removing a file deletes it and its row, and leaves the observation and its notes.
- The migration keeps every existing record and note.
- The **Files** tab shows each state, and the assistant's path and the person's give the same record.
- A chosen folder is used and recorded; a folder that is gone falls back to `~/Downloads`; every caller of
  `DownloadsFolder.url` now goes through `DownloadFolder` (a guardrail test).

## V — Verbinal's data in VOSpace: one manifest of kinds

### What happens today

Verbinal keeps files in the person's VOSpace, and each feature checks its own, or none:

| Folder | Written by | Checked |
|---|---|---|
| `.verbinal/manifests/<image>.json` | Image Discovery's probe jobs | Only for an image probed from this Mac, and only when the discovery sheet opens (`recoverFromVOSpaceIfPresent`). A package list made from another Mac, or from Verbinal for Windows or Linux, is never seen. |
| `.verbinal/exec/inbox`, `.verbinal/exec/out` | Remote Compute | After sign-in, by `RemoteComputeService.resumeWatching`, for the runs this Mac knows. |
| `.verbinal-scripts/` | Batch jobs launched with a `script` | Never. They pile up. |
| `Verbinal-Exports/` | **Upload to VOSpace** of an export | Never. |

Research lives on this Mac only (`verbinal.sqlite`); another Mac starts empty. No file says what Verbinal
keeps in VOSpace: each feature knows its own folder, in code.

### What we want

1. **One manifest declares the kinds.** `.verbinal/manifest.json`, in the person's VOSpace home, says which
   kinds of Verbinal data the person keeps in VOSpace and where each lives: Research, the package lists
   of CANFAR images, Remote Compute runs, staged scripts, exports. It lists **kinds, not items**: each
   kind's folder holds its items, and the folder is their inventory.
2. **The one place to sync from.** Every Verbinal (this Mac, another Mac, Windows, Linux) reads the
   manifest at sign-in, and so knows what to sync and where. A kind turned on from one device is on for
   all of them.
3. **At once, unseen, cheap.** Sync starts right after sign-in, in the background: nothing on screen, no
   notification, no wait. One small request for the manifest when it has not changed; one listing per
   kind's folder; an item is read only when its date or size differs from what this device has.
4. **Research is a kind.** When the person keeps Research in VOSpace, its records (the observation's
   details, notes, tags and quality; not its files, which are each device's) are the same on every
   device.
5. **Nothing is lost by syncing.** Sync never deletes on its own guess. A record the person removes is
   marked removed in VOSpace, and other devices remove it on reading the mark; a missing file means
   nothing.

### The manifest

```json
{
  "format": "verbinal.vospace-manifest",
  "version": 1,
  "kinds": {
    "research":       { "folder": ".verbinal/research",  "format": 1, "since": "2026-10-08T14:02:11Z" },
    "imagePackages":  { "folder": ".verbinal/manifests", "format": 1, "since": "2026-09-12T09:30:00Z" },
    "computeRuns":    { "folder": ".verbinal/exec",      "format": 1, "since": "2026-09-20T17:45:03Z" },
    "stagedScripts":  { "folder": ".verbinal-scripts",   "format": 1, "since": "2026-08-02T11:00:00Z" },
    "exports":        { "folder": "Verbinal-Exports",    "format": 1, "since": "2026-09-01T08:15:40Z" }
  }
}
```

- A kind is declared once, by the first Verbinal that keeps it, and stays until the person turns it off.
- A Verbinal that does not know a kind, or a field, keeps it as it is when it writes the manifest (the
  Windows and Linux apps may add kinds first).
- `format` is the kind's item format; a Verbinal that meets a newer one reads nothing of that kind and
  says so in **Settings ▸ Storage**, rather than guess.
- The manifest holds folder names and dates only: no names of observations, no paths of this Mac, no
  tokens.

### Design

| Part | Job |
|---|---|
| **`StorageManifest`** (model) | The file above, read and written whole; unknown kinds and fields kept (round-trip). |
| **`StorageKind`** (protocol) | One kind: its id, its default folder, its item format, and `sync(_ listing:)`, which compares the folder's listing with this device's state, reads the items that changed, and brings the feature in line. One conformer per kind, owned by its feature: `ResearchKind` (Research), `ImagePackagesKind` (Image Discovery), `ComputeRunsKind` (Remote Compute), `StagedScriptsKind` (batch jobs), `ExportsKind` (export). |
| **`StorageKindCatalog`** | The one place that lists the kinds the app knows. Adding a kind is one conformer and one line. |
| **`StorageSync`** (actor) | Knows the manifest and the catalogue, not the features. After sign-in: the manifest's node (date, size, MD5); the manifest itself only when they changed; then, for each declared kind it knows, one listing of its folder, handed to the kind. Again when Verbinal comes back to the front and the last sync is over 15 minutes old, and at once for a kind whose feature just wrote to VOSpace. Background priority, one request at a time, longer waits while VOSpace fails, nothing after sign-out. |
| **This device's state** | Per kind, each item's date and size as last read, and the manifest's node as last read (`Application Support/Verbinal/StorageSync/state.json`). It is how a sync knows what changed without reading it. |
| **The first manifest** | When there is none, Verbinal writes one that declares the kinds whose folders already exist (the person's probes, runs, scripts and exports, from 1.4.0). Research is declared only when the person turns it on. |

### Research as a kind

| Part | Job |
|---|---|
| **Items** | `.verbinal/research/<key>.json`, one per record (the key: the SHA-256 of the record's publisher ID and cutout, so the same on every device): the record's details, its note (text, quality, tags), when it changed, and `removedAt` when the person removed it. No files, paths or bookmarks: those are each device's. |
| **Writing** | A change to a record in Research (saving, a note, a tag, removing) writes its item, five seconds after the last change (debounced), in the background. The sync watches Research's published state; Research knows nothing of it. |
| **Reading** | A newer item from another device updates the record here. When both changed since the last sync, the newer change wins; the one it replaced is kept on this Mac (`StorageSync/replaced`), and the change log says so without its words (notes stay out of logs). A device marks removed only records it had itself: a failed import is not a removal. |
| **Turning it on** | **Settings ▸ Storage ▸ Keep Research in VOSpace**: off until the person turns it on (their notes, their allocation). Turning it on uploads this Mac's records and declares the kind; another device then sees it declared and syncs it, saying "Research is kept in VOSpace". Turning it off stops the syncing everywhere and leaves the files in VOSpace. |
| **Private only** | Research syncs only while `.verbinal/` is private. If anyone can read it, **Settings ▸ Storage** says so and offers the Storage screen's **Make Private**; Verbinal never changes sharing by itself. |

### The other kinds

- **Image packages:** a package list in VOSpace that this device's cache does not have, or has older, is
  imported; Image Discovery's per-image recovery becomes this kind's sync of one item (DRY).
- **Compute runs:** a result in `exec/out` is handed to its run once; `resumeWatching` reads its results
  from this kind's listing instead of its own.
- **Staged scripts and exports:** counted, with their size, for **Settings ▸ Storage** and **Show in
  Storage**; never deleted by sync.

### Where the person sees it

Nowhere while it runs. **Settings ▸ Storage** (a new section) shows the declared kinds, each with its
folder, how many items, when it last synced and the last failure; **Keep Research in VOSpace**;
**Sync Now**; **Show in Storage**. A failure stays there, and in the decision log; it never interrupts.

### Tools

`list_storage_kinds` (read: the manifest's kinds, each with its folder, items and last sync) and
`sync_storage` (live: sync now). Both in the Storage area of the tool map. Keeping Research in VOSpace is the person's setting: no tool turns it
on. Deleting stays with the storage tools and their kinds of change.

### The shared layout

`docs/vospace-layout.md`: the folders, the manifest, each kind's item format with an example, and the
rules (kinds not items, unknown kinds kept, `removed` marks, newer wins). The Windows and Linux apps
follow it.

### Tests first

- An unchanged manifest costs one request: no read, no listing beyond the declared kinds'.
- No manifest: one is written declaring the kinds whose folders exist, and not Research.
- Unknown kinds and fields survive a write; a newer `format` of a kind is read as nothing, and said.
- A package list in VOSpace that the cache does not have is imported; one it has, unchanged, is not
  read again.
- A late compute result is handed to its run once.
- Research: a note made on one device appears on another; the newer of two changes wins and the other is
  in the log; a removal travels as a mark; a missing item removes nothing; nothing syncs while
  `.verbinal/` is public or the setting is off.
- Scripts and exports are counted, never deleted.
- The sync: background priority, back-off while VOSpace fails, nothing after sign-out, and the catalogue
  lists every kind (a guardrail test, as for the tools).

## Decisions (the person, 2026-10-08)

0. **After a 401:** sign in again by itself with the stored credentials, retry the request, and show the
   sign-in sheet only when that cannot work.
1. **An allowed session** ends after an hour without a call; the person sets the time in **Settings ▸ AI
   Agent**.
2. **An observation's files:** today's main file stays as it is; a new `files` list holds the files
   downloaded one by one.
3. **Where a file goes:** the person sees the download folder where they download, and chooses it;
   Research records where each file went.
4. **The sync:** at once after sign-in, in the background, unseen and cheap.
5. **The manifest:** Verbinal declares in VOSpace which kinds of its data are kept there (Research, the
   CANFAR images' package lists and the rest): kinds, not items. It is the one place every device syncs
   from.
